# Public release privacy gate

Before creating or updating anything publicly visible on GitHub, check the final content for identifiable private organizations, clients, projects and material. This applies to commits, branch names, paths, PRs, Issues, comments, screenshots, generated indexes, package metadata and release assets. Prefer generic scenarios and synthetic fixtures. Keep the private name and alias list, review receipts and source materials outside this repository.

1. Review filenames and the final staged contents, not just the README or a rendered page. For normal Git releases run `python tools/check_publication_privacy.py --denylist PRIVATE_FILE` from the repo. The UTF-8 file must be local and outside the repository, with one literal per line. If it is missing, stop; do not publish an empty-list or skipped check. For uploads through an API, use the same review on the exact candidate tree before writing and verify the published tree afterward.
2. Open anything a text check cannot meaningfully inspect: screenshots and metadata, documents, installer metadata, archive members and generated exports. Use `--opaque-reviews PRIVATE_JSON` only after reviewing the exact bytes; that private JSON maps exact staged paths to lowercase SHA-256 values. A changed asset must be reviewed again. This is not an automated OCR/extraction tool or a server-side push lock.
3. Separately review commit/title/body and author metadata, non-Git uploads and each release filename and artifact. Use a public no-reply Git identity when available. Do not use a match count as approval for uncovered material, and never include the private aliases in rejection messages or public commit descriptions. The repository's own public URL is not permission to link other personal or private projects.
4. Once the check and manual review pass, upload only the reviewed evidence and verify the remote result. If material cannot be verified or must stay identifiable, omit it and raise the issue privately. A cleanup commit does not erase earlier history, tags, release assets or copies.

An installer identity change requires a conducted migration/retention test before a new installer is released. Do not release an untested upgrade path.
