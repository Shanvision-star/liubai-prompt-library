# 设计减法：删掉干扰，保留信息与功能

> 中文改编 v001 · 2026-10-23 · 基于 [pbakaus/impeccable](https://github.com/pbakaus/impeccable/blob/5cb95eea9c96479f57afe0732a45470d30183326/skill/reference/distill.md) 的公开指令，已修改。来源、原版依赖和许可见 [SOURCE.md](SOURCE.md) 与 [LICENSE.txt](LICENSE.txt)。实际效果：**未测试（untested）**。

填写或提供 `{{变量}}` 对应材料；没有提供的项目按正文缺失处理规则执行。以下代码块可完整复制：

```text
请帮助简化 {{design_material}}，让 {{audience}} 更容易完成 {{primary_task}}。

本次必须保留 {{must_keep}}；允许修改 {{editable_scope}}，不能修改 {{out_of_scope}}。未说明可以改文件时，先交付建议，不直接实现。

1. 先从实际材料提取页面的主目标、支持信息和次要任务。列出不可删内容：关键事实、必要说明、主要操作、权限状态、错误恢复以及辅助技术需要的信息。缺少业务依据时标记，不自行判定无用。
2. 找出最影响目标的冗余：重复信息、抢注意力的装饰、没有语义作用的容器、相同功能的多个入口、过多同级样式或绕路步骤。
3. 建立清单：元素/区域｜当前作用｜保留/删除/合并/延后展示｜理由｜风险｜复查办法。‘不喜欢’不是充分的删除理由；不要只按出现频率判断价值。
4. 先提出最小可行的减法方案。说明主体、分组、层级和阅读顺序将如何更清楚。可以减少样式种类，但不要机械限制为一种字体或两种颜色；专业工作台可保留必要的信息密度。
5. 若已授权实施，沿用现有技术栈和组件，只修改本次范围。保留可恢复的前版。不要为视觉简洁迁移架构或删除未经核实的代码。

输出减法清单、前后结构对照、保留理由、风险和验证结果。若没有真实用户测试，只能描述可观察的变化，不宣称认知负担、转化率或操作效率已改善。

Loop 与停止条件：
如已授权修改且有可检查的材料，最多做 2 轮‘提出删减 → 小范围修改 → 同一任务复查’。每轮只处理优先级最高的一组冗余，保留前版与改动清单。检查必需信息仍可找到、关键操作仍可完成、错误与权限反馈仍可见。任一项退化就恢复相关改动。达到既定清晰度且没有功能损失即停止；不能验证、需要牺牲已冻结内容、连续一轮无可观察改善或达到上限时停止，交付取舍而非继续删减。
```
