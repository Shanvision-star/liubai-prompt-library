# 制作思路

### 目标效果与画面顺序

这条方案把真实产品的一条用户路径压缩为连续 UI 演示：从品牌标志进入账号识别，再显示用户分布与匹配、标签切换、RSVP 和搜索，最后回到标志。它不是任意组件的展示集，产品 URL、实际数据和品牌资料会直接决定每个界面的内容。

需要先厘清 pin 在目标产品里代表什么，再排它与地球视图的衔接；原文并未给出其含义，本解读不替它定为地图定位针或其他控件。RSVP 对应出席回复这一功能语境，若目标产品没有该功能，复用时应明确替换为真实存在的操作。

### 动画方法

主形状的宽高、圆角、颜色、位置由 draw(t) 统一计算，内部文字和数据另设出现、停留和离开区间。关键约束是内容在容器开始变形之后才出现，并在下一次形变前离开。这样既能让观众看到“容器变化”，又不会把两套界面叠在一起。

强调色应作为能在状态间迁移的视觉元素，例如某个标记或选中指示，而不是把整块黑色直接淡变成品牌色；这是原文明示的转场限制。标签指示条两端分别响应，让它先拉长再收拢。真实点击、输入和一次拖动要与反馈同轴编排，不能让页面先变化、光标随后补点。

### 工具与素材

原文明示：单个 HTML、一个 canvas、draw(t)、无头 Chrome、ffmpeg、H.264、yuv420p；60fps，每帧平均 6 个子帧；1:1、16:9、9:16 等用户确认的画幅。输入素材是产品及 URL、8–12 个状态、每状态真实数据、品牌颜色、字体和强调色。

原文未要求 Playwright、GSAP、numpy，也没有指定音乐或音效。可选建议：用状态表管理真实数据字段和每个画幅的布局；若选用浏览器自动化工具驱动逐帧渲染，那是实现选择，并非此条原文点名的工具。

### 落地步骤与验收点

1. 从产品资料建立状态清单，逐项确认真实内容来源。把“用户名—身份确认—用户分布—匹配—回复—搜索”涉及的数据和文案对应到画面，避免用临时虚构数字填空。
2. 先制作各状态静态画面，检查长用户名、匹配列表和 RSVP 信息在三种画幅内的阅读层级，再建立单一形状的连续变化。
3. 编排 120 BPM 网格上的事件，标出光标点击、打字、唯一一次拖动及文字切换区间。原文残词 bea 不作为新增要求的依据；每拍一帧的预检要求本身来自完整的 export 段。
4. 输出每拍一帧的缩略图总览，查拥挤、状态缺失及文案重叠。可选建议：逐画幅核对光标目标与组件中心是否一起随布局调整，避免竖屏时指针点到旧位置。
5. 在无头 Chrome 中按 60fps、6 个子帧平均的方式渲染，再通过 ffmpeg 编码为 H.264 + yuv420p，并行导出所需画幅。验收应核对实际尺寸比例、文字可读性、强调色迁移方式、首尾帧一致性；没有这些结果前不能声称已完成验证。

### 如何替换后复用

先把此处状态换成自家产品的实际主路径，再一并替换 logo、URL、账号字段、按钮文案和数据。保留 draw(t)、单形状无切镜、一次拖动和内容进出窗口等运动规则，重新安排与新路径对应的节拍。新数据会改变列表高度和文字长度，不能只替换文字而沿用旧画框；三种画幅须分别检查。原文未指定总时长，不应把其他模板的 14 秒或 7 小节移植为本条硬约束。
