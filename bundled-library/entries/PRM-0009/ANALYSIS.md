# PRM-0009 设计逻辑与使用方法

把界面从理想演示扩展到真实输入、失败和恢复情境，保护用户已完成的工作。

## 为什么入选

UI 已经有正常流程，需要处理加载、无数据、失败、权限、极端文本与重复提交。 源文具有明确任务、具体步骤和可检查的产物，适合作为高质量候选。此处是结构评审，不是效果认证。

## 原作者公开的方法

以下依据[固定版本原文](https://github.com/pbakaus/impeccable/blob/5cb95eea9c96479f57afe0732a45470d30183326/skill/reference/harden.md)归纳：原文覆盖文字溢出、国际化、网络和接口失败、加载空状态、输入验证与交互边缘情形，并要求通过极端数据和失败场景验证，而不只检查正常页面。

## 我的设计逻辑分析

以下是本次整理者对方法作用的解释，不是作者未公开的内部思考：界面的可信度往往取决于失败时如何反馈和恢复。把状态与恢复动作成对定义，可以暴露‘出了错但不知道下一步做什么’的缺口；保留用户输入并区分客户端模拟与服务端事实，可以减少假成功与重复操作。

## Loop 是否需要、怎样写

**有可控测试环境时建议使用，最多 3 轮。**

```text
对已授权修改且能安全构造的状态，最多 3 轮‘触发失败 → 记录预期与实际 → 修复 → 重跑失败与正常路径’。先处理数据丢失、主任务受阻、权限误导和重复提交，再处理视觉问题。每轮记录输入、状态来源、步骤、修改和结果。已选状态通过且正常路径不退化即停止；缺少接口约定或测试能力、连续一轮无新进展、修改超出范围或达到上限时停止并报告。不能真实验证的场景保留为待验证，不能通过删除场景或吞掉错误让清单变绿。
```

## 使用示例与边界

- 使用示例：为提示词保存表单检查超长内容、保存失败后保留输入、重复点击、无权限和重试反馈。
- 不宜直接外推：前端防重复点击不能证明服务端幂等；模拟错误界面不能证明后端正确拒绝或恢复请求。
- 证据现状：源文提供具体边界输入与检查场景；本次仅完成指令改编，未执行真实界面回归、接口或幂等验证。
- 实际效果状态：`untested`。已完成的检查仅为来源、文件完整性、分类、版本与文本结构；未进行真实模型生成、用户偏好测试或项目运行。

## 如何验证这条提示词是否对你有效

选择一个代表性任务，冻结输入、模型与运行条件，用原版适用环境和优化版各生成一次；原版依赖不齐时，将基线改为你现用提示词并明确标注。记录输出、失败项、可观察指标和你的取舍理由。先看是否达成上述可检查产物，再记录偏好；一次胜出只是样例证据，不能推广为通用结论。把实际结果写入本条反馈并保留失败样例后，再决定是否生成 v002。
