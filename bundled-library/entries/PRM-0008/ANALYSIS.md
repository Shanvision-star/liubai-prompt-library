# PRM-0008 设计逻辑与使用方法

围绕同一核心任务调整布局、信息顺序与输入反馈，明确浏览器模拟与真实设备证据的差别。

## 为什么入选

桌面看起来正常，但手机出现溢出、操作被遮挡、表格难用或触摸失败。 源文具有明确任务、具体步骤和可检查的产物，适合作为高质量候选。此处是结构评审，不是效果认证。

## 原作者公开的方法

以下依据[固定版本原文](https://github.com/pbakaus/impeccable/blob/5cb95eea9c96479f57afe0732a45470d30183326/skill/reference/adapt.md)归纳：原文按屏幕、输入方式、网络和任务情境调整体验，强调移动端不只是缩小桌面；对手势给出真实输入检查，并要求声明模拟视口、合成触摸、浏览器引擎与真机的证据区别。

## 我的设计逻辑分析

以下是本次整理者对方法作用的解释，不是作者未公开的内部思考：响应式的核心是同一任务在不同约束下仍可完成。小屏常需改变信息顺序或展示方式，触摸也不能依赖悬停。先建立情境与任务矩阵，再修改高风险断点，可以比仅看几个截图更早暴露真正的阻断。

## Loop 是否需要、怎样写

**有页面与工具时建议使用，最多 3 轮。**

```text
在用户已授权实现且可运行目标页面时，最多 3 轮‘检查情境矩阵 → 修复最高影响失败 → 复测失败与相邻情境’。每轮保存视口、浏览器、输入方式、操作步骤和前后结果。优先处理主任务受阻、遮挡和误操作，不为循环增加新平台。目标情境通过即停止；连续一轮无法减少已确认失败、缺真机/材料/权限、需要改业务范围或达到上限时停止，列出未覆盖项。新改动导致原情境退化时恢复或修正相关改动。纯建议任务只交付矩阵与方案，不伪造测试结果。
```

## 使用示例与边界

- 使用示例：检查提示词搜索页在窄屏下筛选是否遮住结果、长标题是否溢出、复制按钮是否能用键盘操作。
- 不宜直接外推：浏览器尺寸模拟不能证明手机键盘、真实多点触控、设备性能及所有浏览器都可用。
- 证据现状：公开原文包含具体 Web 适配和手势检查办法；本次没有运行页面、浏览器输入或真实设备测试。
- 实际效果状态：`untested`。已完成的检查仅为来源、文件完整性、分类、版本与文本结构；未进行真实模型生成、用户偏好测试或项目运行。

## 如何验证这条提示词是否对你有效

选择一个代表性任务，冻结输入、模型与运行条件，用原版适用环境和优化版各生成一次；原版依赖不齐时，将基线改为你现用提示词并明确标注。记录输出、失败项、可观察指标和你的取舍理由。先看是否达成上述可检查产物，再记录偏好；一次胜出只是样例证据，不能推广为通用结论。把实际结果写入本条反馈并保留失败样例后，再决定是否生成 v002。
